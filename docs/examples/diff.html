I002 — JWT auth flow

The auth flow issues a short-lived access token plus a long-lived refresh token. The access token carries a 15-minute expiry; the refresh token lasts seven days. Verification is constant-time on the signature and runs at every protected endpoint.

Refresh tokens rotate on every use. The new token replaces the old one in the user's token-family ledger. Reuse of an old token is treated as a stolen-credential signal and revokes the entire family. Revised in v0.4: rotation was added; v0.3 used long-lived static refresh tokens.

Layer-2 audit invokes a second, cheaper model on every done-flip and confirms the verifyCmd was load-bearing rather than a passing tautology. Without this, a clever build agent can author verifyCmd: true and pass instantly.

I004 — Rate limiting

Login is capped at ten attempts per IP per minute, with a fifteen-minute lockout after the cap is hit. The implementation uses a sliding-window counter in Redis, with an in-memory fallback for local dev so contributors don't need Redis to run the test suite.

In addition to per-IP, we now cap per-account at five failed attempts per ten minutes regardless of source IP. This catches the slow-and-distributed credential-stuffing pattern that per-IP alone misses.
